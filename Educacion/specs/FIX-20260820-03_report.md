## A. Síntoma y alcance

- Producción (Vercel): `/alumnos` crashea con **React error #482** ("async Client
  Components are not supported") al abrir la entrevista inicial de un alumno. La página
  servidora renderiza (SSR intacto); el fallo es **client-side**, al pulsar el botón
  "Entrevista" de una fila: el árbol React completo de la ruta cae sin error boundary.
- Alcance funcional: flujo de entrevista inicial del niño (carga/guardado/archivado)
  inutilizado en producción. El resto de la gestión de alumnos (listar, buscar, agregar,
  editar, eliminar) renderiza, pero cualquier interacción posterior al crash queda muerta
  hasta recargar.
- El build NO detecta el defecto (`pnpm build` pre-fix pasa): la validación de componentes
  async es de render, no de compilación, y `/alumnos` es `force-dynamic` con el modal
  cerrado en el SSR inicial. Por eso pasó CI y despliegue.

## E. Causa raíz

`app/(app)/alumnos/entrevista-dialog-content.tsx` declaraba `export async function
EntrevistaDialogContent` (patrón Server Component) **sin directiva**, y era importado y
renderizado por `alumnos-manager.tsx`, que es `'use client'`. Todo módulo sin directiva
importado desde el árbol cliente se compila como código cliente; React no soporta
componentes de función async en el cliente, así que al montar el diálogo (click en
"Entrevista") el render devuelve una Promise y React rompe el árbol: #482 en producción.
El defecto es invisible para el build y para el SSR (el modal inicia cerrado), por eso
llegó a producción. Causa confirmada con reproducción runtime pre-fix, detección estática
del borde exacto del grafo y contra-reproducción post-fix.

Nota de diseño preexistente que agravó el defecto: el componente recibía callbacks
`onSaved`/`onError` desde el cliente, lo que nunca fue compatible con un Server Component
(las funciones no cruzan la frontera servidor→cliente); el módulo sólo pudo vivir como
código cliente, donde `async` es ilegal.

## F. Solución aplicada (conservadora, sin alterar contrato ni comportamiento)

Reescritura de `app/(app)/alumnos/entrevista-dialog-content.tsx` (+107/−17) como
**Client Component no-async** (`'use client'` explícito):

- Carga la entrevista existente al montar el modal invocando la server action
  `getEntrevista` desde el cliente (patrón válido: las acciones de un módulo `'use server'`
  son invocables desde Client Components). Sin `use()` y sin `await` en render: la lectura
  vive en un `useEffect` con guarda de cancelación (`active`) por desmontaje/cambio de
  alumno.
- Estados de lectura: `loading` (`entrevista-dialog-loading`, role=status) → `error`
  (`entrevista-dialog-error`, role=alert, con botón `Reintentar` que re-ejecuta la acción)
  → `ready` (form con `initial` proyectado o `null` si no hay entrevista).
- **Sin cambios en:** contrato de props del componente (mismas 6 props, mismo export);
  `getEntrevista`/`upsertEntrevista`/`archivarEntrevista` (RLS + ownership + gate A1
  server-side + validación literal v2 + archivado C1+C2 + no-borrado); proyección de datos
  al form (mismos 4 campos `fecha_aplicacion/estado/respuestas/directorio`);
  `EntrevistaInicialForm` (literalidad de los 3 bloques, gate de aviso en UI, archivado);
  `alumnos-manager.tsx` (**cero ediciones** — botones de alumnos intactos); exclusión IA
  (AC-21 re-verificado). El gate A1 sigue aplicado en UI por el form y reforzado
  server-side por `upsertEntrevista`/`archivarEntrevista`.
- Diferencia de comportamiento deliberada (instruida): ante `getEntrevista` con error, el
  diálogo muestra estado de error con reintento en lugar del fallback silencioso a form
  vacío del código original (que además nunca llegó a funcionar en producción).
