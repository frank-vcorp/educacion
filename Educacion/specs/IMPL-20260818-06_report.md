### 🔴 P0 — Migración 0018 (`planeacion.metadata jsonb`)

**Archivo:** `Educacion/supabase/migrations/0018_planeacion_metadata.sql`

**Decisión arquitectónica (validada INTEGRA):**
- Columna `metadata jsonb NOT NULL DEFAULT '{}'::jsonb` en `planeacion`.
- Índice GIN `idx_planeacion_metadata_gin` (jsonb_path_ops) para queries futuras sobre `modalidad_data`.
- NO toca RLS: `planeacion_docente_own` (migración 0014) sigue filtrando por `docente_id + cct`.
- Patrón consistente con `docente.configuracion_m4 jsonb` (SPEC_TEC_02 §5.3.1).

### 🟡 P1.3 — Validación condicional completa en server action

**Archivo:** `Educacion/services/planeaciones/planeacion-actions.ts`

**Cambios:**
- Nuevo sub-esquema `MetadataSchema = z.object({ modalidad_data: z.record(z.unknown()).default({}) }).default({ modalidad_data: {} })`.
- `BaseSchema` acepta `metadata` opcional.
- `validarModalidad()` reescrito con validación completa:

```ts
case 'unidad_didactica':
  - bancoPalabras.length ∈ [1, 10]
  - metadata.modalidad_data.sesiones_semana con ≥1 día con título no vacío
  → 'Unidad Didáctica necesita al menos un día con sesión (L M M J V)'

case 'rincones':
  - metadata.modalidad_data.rincones.length ≥ 2
  - cada uno con nombre no vacío
  → 'Rincones requiere al menos 2 rincones con nombre'

case 'centros_interes':
  - metadata.modalidad_data.tema.length ≥ 3
  - metadata.modalidad_data.preguntas_det.length ≥ 1
  → 'Centros de Interés necesita un tema y al menos una pregunta detonadora'

case 'taller_critico':
  - metadata.modalidad_data.fases.length === 3
  → 'Taller Crítico necesita 3 fases (reflexión, producción, socialización)'

case 'abj' | 'proyecto_comunitario':
  - sin validación extra (sesiones se modelan en `sesion` con fase_interna)
```

- INSERT ahora persiste `metadata: { modalidad_data: data.metadata?.modalidad_data ?? {} }` (línea ~185).

### 🟡 P1.4 — Confirmación de cambio de modalidad

**Archivo:** `Educacion/components/planeaciones/wizard-planeacion.tsx`

**Cambios:**
- Helpers puros (testeables):
  - `MODALIDADES_LABELS: Record<Modalidad, string>` para mensajes.
  - `tieneDatosEspecificos(form, modalidad)` — bool.
  - `limpiarDatosEspecificos(prev, nueva)` — devuelve `FormState` con campos de modalidad reseteados, manteniendo comunes (nombre, problema, campos, pdas, ejes, periodo).
  - `buildModalidadData(form)` — convierte el state del wizard al contrato JSONB por modalidad.
- State nuevo: `cambioModalidad: { from, to } | null`.
- `cambiarModalidad(m)` ahora:
  - Si `m === form.modalidad`: no-op.
  - Si NO hay datos específicos: aplica cambio silencioso.
  - Si SÍ hay datos específicos: abre Dialog de confirmación.
- `confirmarCambioModalidad()` aplica `limpiarDatosEspecificos` y reinicia a paso 1.
- `cancelarCambioModalidad()` cierra el Dialog sin cambiar modalidad.
- `guardar()` envía `metadata: { modalidad_data: buildModalidadData(form) }` en el payload.
- Mensaje del Dialog: "Al cambiar a [NUEVA], se borrarán los datos específicos de [ANTERIOR] (banco de palabras, sesiones, rincones, tema, preguntas o fases). Los campos comunes (nombre, problema, campos formativos, PDA, ejes, periodo) se conservan."
