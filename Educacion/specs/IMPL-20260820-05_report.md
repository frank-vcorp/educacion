## 2. P1-1 — Viewport meta ausente en el fixture HTML

### 2.1 Problema

`QA-20260820-03` §D documentó que el spec ejecutable
`e2e/entrevista-inicial.mobile.spec.ts` (introducido por IMPL-04 §5.2.A
para resolver P3-4 de QA-20260820-02) **fallaba en el proyecto
Playwright `mobile`** con la aserción:

```text
expect(metrics.docScrollWidth).toBeLessThanOrEqual(375)
  Received: 981
```

El viewport de Playwright sí era 375×812 (asserción `vp` PASS), pero
**el navegador mobile** (Pixel 5, `isMobile: true`) renderizaba el HTML
a ~980 px de ancho por defecto, porque el `<head>` del fixture no
declaraba `<meta name="viewport" content="width=device-width, ...">`.
En el proyecto `chromium` (Desktop Chrome, sin `isMobile`) el defecto
de rendering cae a 375 px por la propia naturaleza del dispositivo, por
lo que el test pasaba allí aunque el fixture siguiera mal.

Esto invalidaba la afirmación de IMPL-04 §5.3.D ("el spec es
descubierto por ambos proyectos… doble gate de cobertura"): el doble
gate **no existía realmente** porque en `mobile` el test fallaba.

QA-20260820-03 §D P1-1 ya fijó la condición de cierre:

> `pnpm exec playwright test e2e/entrevista-inicial.mobile.spec.ts
> --project=mobile` → PASS, con `docScrollWidth=375` y métricas
> equivalentes a la corrida chromium.

### 2.2 Solución

Añadir la meta-etiqueta estándar al `<head>` del fixture HTML,
exactamente como recomienda la propia QA (P1-1, recomendación) y como
la consignó Frank en la instrucción vigente. Se eligió el formato
mínimo solicitado (`content="width=device-width"`) — el `initial-scale`
se omite porque el default de los navegadores modernos es `1.0` y
`width=device-width` por sí solo ya cubre la condición de cierre
(`docScrollWidth=375` con la misma métrica que en `chromium`).

**Cambio aplicado (1 archivo, 4 líneas añadidas, 0 borradas):**

```diff
--- a/e2e/entrevista-inicial.mobile.spec.ts
+++ b/e2e/entrevista-inicial.mobile.spec.ts
@@ -47,6 +47,10 @@
 <head>
 <meta charset="utf-8" />
+<!-- IMPL-20260820-05 (P1-1 de QA-20260820-03): viewport meta para que el navegador
+     en --project=mobile (Pixel 5, isMobile:true) renderice el HTML al ancho
+     del dispositivo y no a ~980px (default mobile sin meta). -->
+<meta name="viewport" content="width=device-width" />
 <title>Entrevista inicial — fixture 375x812</title>
 <style>
```

Notas técnicas del cambio:

- **No** se tocó el cuerpo de la `FIXTURE_HTML` (CSS inline, grid, 21
  preguntas literales, gates, etc.): el contrato del fixture y los
  valores que valida IMPL-04 §5.3.A se preservan exactamente.
- **No** se tocó `test.use({ viewport: { width: 375, height: 812 } })`:
  sigue aplicando 375×812 al viewport de Playwright; el meta hace que
  el navegador mobile respete ese ancho en lugar de asumir 980 px.
- **No** se tocó `playwright.config.ts` (`Pixel 5` sigue siendo el
  dispositivo del proyecto `mobile` con `isMobile: true`).
- El comentario HTML al lado del meta etiqueta la trazabilidad
  `IMPL-20260820-05 → P1-1 de QA-20260820-03` sin meter IDs en código
  fuente productivo (sigue siendo doc-text dentro de un fixture
  auxiliar que ya llevaba identificadores de IMPL anteriores).

- **Bajo (R-IMPL-05-1):** el spec
  `e2e/entrevista-inicial.mobile.spec.ts` sigue usando CSS inline
  (no el bundle real de Tailwind), exactamente igual que en IMPL-04.
  El meta tag **no cambia** esa limitación: si Tailwind cambiara el
  valor de `max-w-3xl` o `w-full`, este test seguiría sin detectarlo
  automáticamente. Riesgo ya documentado en IMPL-04 §10.2 (R-IMPL-04-1)
  y QA-20260820-03 §D P3-1; la verificación con Tailwind real + `0022`
  aplicada sigue siendo gate de staging.
- **Nulo (R-IMPL-05-2):** el meta tag no introduce regresión en
  `chromium` (ver §6.3), no afecta al DOM de la app ni al bundle
  Next.js, y no se ejecuta en producción (solo en el spec de
  viewport).

### 7.3 Compatibilidad
