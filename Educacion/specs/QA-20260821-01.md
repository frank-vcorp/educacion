## 4. Hallazgos priorizados

### F-1 [P2] — e2e `entrevista-inicial-stepper.mobile.spec.ts` falla por assertion incorrecta (no por la implementación)

- **Evidencia:**
  - Comando: `pnpm exec playwright test e2e/entrevista-inicial-stepper.mobile.spec.ts`
  - Resultado: 2 failed (`chromium` y `mobile` projects).
  - Error literal: `expect(initial.dialog.maxHeight).toMatch(/(90vh|90dvh)/);` — `Received string: "730.8px"`.
  - Causa: la assertion compara el **computed style** (`getComputedStyle(dialog).maxHeight`), que el navegador SIEMPRE devuelve en píxeles resueltos (`"730.8px"` = 90% de 812px viewport), NO el valor CSS original. La regla CSS del fixture es `max-height: 90vh; max-height: 90dvh;` — el browser resuelve la segunda (con `dvh`) a `730.8px`. La regex `/(90vh|90dvh)/` nunca matchea un valor computado en píxeles.
  - Inspección del PNG del failure (`test-results/.../test-failed-1.png`): el fixture renderiza correctamente con max-height 730.8px (≈ 90% de 812), los 3 botones del stepper visibles, el footer accesible y `aria-current="step"` en el botón 1. **La implementación del fixture reproduce fielmente la nueva estructura**; el gate no verifica lo que pretende.
- **Impacto:** el gate MOBILE-1 (única verificación e2e añadida por IMPL-20260821-01) **no pasa**. La implementación del componente real es correcta (verificada manualmente y por unit tests), pero el e2e fixture que la representa tiene una assertion rota. CI reportará este test como rojo aunque el código funcione.
- **Reproducción:** `pnpm exec playwright test e2e/entrevista-inicial-stepper.mobile.spec.ts` (entorno con Chromium) → 2 failed con el error descrito.
- **Owner recomendado:** SOFIA (fix de test, no de producto).
- **Condición de cierre:** cambiar la assertion para validar el resolved max-height en píxeles contra el 90% del viewport (e.g., `expect(parseFloat(initial.dialog.maxHeight)).toBeCloseTo(812 * 0.9, 0)` o `toBeLessThanOrEqual(812 * 0.9)`) o comparar contra el `max-height` declarado vía `window.getComputedStyle(dialog, null).getPropertyValue('max-height')` — no la versión computed. Alternativa: evaluar la regla CSS con `document.styleSheets` (más complejo; no recomendado). El cambio está contenido al spec e2e, no toca código de producto.
- **Severidad QA:** P2 (caso borde de observabilidad del gate; implementación correcta; el test es la pieza rota).

### F-2 [P3] — `dialog-content` unit test verifica la clase `max-h-[90dvh]` por regex, pero NO valida la altura resuelta en el render real

- **Evidencia:** `tests/unit/components/entrevista-dialog-content.spec.tsx:50` — `expect(dialog?.className ?? '').toMatch(/max-h-\[90dvh\]/);` usa `className` (string), no `getBoundingClientRect().height`. En jsdom (sin layout), `getBoundingClientRect` devuelve 0, así que validar la altura resuelta no es viable en unit test. El integration con Tailwind (cn + tailwind-merge) sí está cubierto implícitamente por el `e2e/entrevista-inicial-stepper.mobile.spec.ts` — pero ese test está roto (ver F-1).
- **Impacto:** smoke test del modal sin verificación dimensional real. Aceptable para unit (limitaciones de jsdom), pero refuerza la necesidad de arreglar F-1.
- **Owner:** SOFIA (cerrado al arreglar F-1).
- **Condición de cierre:** el test e2e F-1 corregido cubre la validación dimensional real; el unit test de dialog-content cumple función de regresión de marca/clase.
- **Severidad QA:** P3 (mejora de evidencia, no bloqueante).
