## Decisiones internas

### D1. Persistencia limitada al esquema actual (sin migrar BD)

**Hecho:** La SPEC indica "No necesitas cambiar BD" porque el `CHECK` de
`modalidad` ya cubre las 6 opciones. La BD solo tiene una columna relacionada:
`planeacion.banco_palabras text[]`. No existen columnas para `rincones`,
`preguntas_det`, `tema_centro_interes`, `sesiones`, `fases`, etc.

**Decisión:** Para no modificar la BD (que sería un cambio de contrato no
autorizado en esta sesión), el wizard valida las reglas de cada modalidad en el
cliente y el server action valida el shape, pero solo persiste en BD:
- `modalidad` (siempre)
- `banco_palabras` (solo para `unidad_didactica`)
- campos compartidos: `nombre`, `problemaContexto`, `camposFormativos`, `pdas`,
  `ejesArticuladores`, `ajustesRazonables`, `periodoInicio`, `periodoFin`.

**Limitación conocida:** Los datos específicos de las modalidades `rincones`,
`centros_interes`, `abj` y `taller_critico` (lista de rincones, preguntas
detonadoras, tema, fases) **no se persisten en BD**; solo se validan para
satisfacer el contrato del wizard. **Esto bloquea el caso de uso de edición
posterior de esos campos desde la pantalla de detalle.**

**Recomendación (no resuelta en esta sesión):** INTEGRA/Frank deben decidir
entre:
- **(A)** Agregar una columna `metadata jsonb` a `planeacion` (migración
  autorizada explícitamente) → habilita persistencia completa de las 5
  modalidades no-MVP.
- **(B)** Crear tabla hija `planeacion_modalidad_detalle` con FK a `planeacion`
  → más limpio, normaliza por modalidad.
- **(C)** Mantener como MVP solo persistiendo el shape → las modalidades
  nuevas quedan como wizards de "vista previa sin guardar detalle".

### D2. Sub-componente `PreguntasDet` extraído por `react-hooks/rules-of-hooks`

ESLint reportó que `useState` no podía usarse dentro de una función `renderXxx`
dentro del componente principal (no es componente, no es hook). Se extrajo a un
componente de módulo independiente `PreguntasDet` que recibe `value` y
`onChange` por props.

### D3. Calendario semanal: `@dnd-kit` + fallback manual

El SPEC exige drag & drop. Se usó `@dnd-kit/core` (ya en `dependencies`).
Como DnD no es accesible sin pointer/keyboard, agregué un `<details>` con inputs
manuales por día como fallback. El prompt() para asignar títulos desde la celda
es temporal hasta que Frank apruebe un editor inline más rico.

### D4. `descripcionPorPaso` con `Record<string, string>`

Por el flag `noUncheckedIndexedAccess: true` en `tsconfig.json`, `steps[paso-1]`
se tipa como `string | undefined`. La fallback explícita `?? 'Modalidad'`
permite tipar `stepName: string`.

### D5. `MODALIDADES` exportado como constante testeable

Para no necesitar React Testing Library solo para validar el catálogo, el
selector exporta la constante `MODALIDADES` y el tipo `Modalidad`. Esto permite
verificar invariantes (6 modalidades, nombres canónicos) en tests unitarios.

## Issues encontrados

### I1. Workaround `TMPDIR=/home/frank/repos/educacion/.cache`

El sandbox dev tiene `/tmp` (tmpfs) con solo 2.3 GB libres. `pnpm test`,
`pnpm build` y `vercel deploy` fallan con `Error: Unknown system error -122` si
no se exporta `TMPDIR` apuntando a un filesystem con espacio (el directorio
`.cache/` del repo funciona). El reporte previo `IMPL-20260817-04_report.md`
ya documentó esto. **Acción sugerida (no bloqueante):** agregar la variable a
un `.envrc` del repo o documentarlo en el README del proyecto.

### I2. Limitación de persistencia (decisión D1 arriba)

El wizard valida todas las modalidades, pero las 5 nuevas no persistirán sus
datos específicos (rincones/preguntas/fases) en BD. Solo se guarda
`modalidad='X'` + `banco_palabras` (cuando aplica) + campos compartidos. Si
Frank quiere ver los datos en la pantalla de detalle `/planeaciones/[id]`,
necesitamos decisión arquitectónica (A, B o C de D1).

### I3. Tests E2E no ejecutados

El sandbox no permite levantar Supabase localmente + navegador headless de
forma estable. Los E2E (Playwright) no se ejecutaron en esta sesión. La
cobertura del flujo es a través de:
- Tests unitarios de los nuevos componentes (8 tests nuevos)
- Build production exitoso
- Verificación HTTP de la app desplegada

### I4. No se modificó `Educacion/specs/SPEC_TEC_*.md`

Conforme a la restricción CRÍTICA de la SPEC. No toqué ningún `SPEC_TEC_*`.

### I5. No se implementó IA real

Conforme a la restricción. Las 6 sugerencias estáticas existentes para el
campo "problema del contexto" (de `sugerencias-data.ts`) siguen siendo
suficientes; las modalidades nuevas no requieren sugerencias automáticas en
esta iteración.
