## F. Detalle de diseño

### F.1 — Estrategia de mocks

`vi.mock` con `vi.hoisted` para declarar los arrays capturadores (`signUpCalls`, `signInWithOtpCalls`, `signInWithPasswordCalls`, `headersMock`) **antes** de definir el módulo mockeado. Esto evita el problema típico de "cannot access before initialization" en mocks de Vitest.

Mocks:
- `next/headers` → `headers()` → función mockeada (`headersMock`) cuyo resultado implementa `get(name)` con un switch case-insensitive sobre `x-forwarded-host`, `x-forwarded-proto` y `host`, devolviendo `null` por defecto.
- `lib/supabase/server` → `createClient()` → devuelve un fake client cuyo `auth` tiene `signUp`, `signInWithOtp`, `signInWithPassword` y `signOut` como `vi.fn(async ...)` que **registran los argumentos** en los arrays capturadores antes de devolver un resultado controlado (`{ data: { user: { id: 'fake-user-id' } }, error: null }` para signUp/signIn; `{ error: null }` para signOut).

NO se mockea `@/lib/auth/origin.resolveOrigin`: el test usa el helper real para ejercitar la cadena completa `actions.ts → resolveOrigin → process.env/headers`. Esto es deliberado: la cobertura del helper puro ya está exhaustivamente probada en `tests/unit/lib/auth-origin.test.ts`; aquí la prioridad es asegurar la **conexión** actions → helper, que es exactamente el gap que F1 señala.

### F.2 — Control de env vars por test

Helpers `setProdEnv` / `setDevEnv` mutan `process.env` con un cast controlado `process.env as unknown as Record<string, string | undefined>` (necesario porque `@types/node` declara `NODE_ENV` como literal readonly). `beforeEach` reinicia los arrays capturadores y el `headersMock`; `afterEach` borra las env vars para no contaminar tests posteriores.

Para cada test se fuerza `VERCEL_ENV` y `NODE_ENV` a `'production'` (rama `isProd` se activa con cualquiera de los dos; usar ambos blinda el test contra un refactor futuro que cambie la disyunción).

### F.3 — Aserciones "exactas"

El usuario pidió verificar "exactamente `https://educacion-nem-mvp.vercel.app/auth/callback?redirect=/onboarding` o `/dashboard`". Para `register` y `sendMagicLink` las acciones producen esa cadena literal (no URL-encoden el redirect hardcodeado). Para `login(magic)` la acción L92 aplica `encodeURIComponent(redirectTo)`, así que la cadena capturada es `https://educacion-nem-mvp.vercel.app/auth/callback?redirect=%2Fdashboard`. Para mantener la cobertura de seguridad sin atar el test a una inconsistencia de código (no de seguridad), en el bloque `login(magic)` se verifica:

```ts
const u = new URL(call.options.emailRedirectTo);
expect(u.origin).toBe(PROD_ORIGIN);
expect(u.pathname).toBe('/auth/callback');
expect(u.searchParams.get('redirect')).toBe('/dashboard');
```

Equivalente semántico y portable a un refactor que elimine el encodeo redundante. El comentario en el test documenta esta decisión para no confundir a futuros mantenedores.

### F.4 — Inconsistencia detectada (no resuelta)

El test expone una inconsistencia menor de código (no de seguridad): `register` (L136) y `sendMagicLink` (L167) hardcodean `?redirect=/onboarding` / `?redirect=/dashboard` sin `encodeURIComponent`; `login` (L92) sí lo aplica. Para rutas como `/dashboard` el encodeo es redundante (URL.canónica de `/` no requiere escape), por lo que el riesgo es cero en el flujo actual. Anotado aquí como observación para INTEGRA (P3-Baja, **fuera del alcance de este FIX**).

### F.5 — Sin cambios de producción

El usuario pidió "no cambies código de producción salvo lo mínimo si el test lo exige". **Cero cambios de producción**: el código de `lib/auth/actions.ts`, `lib/auth/origin.ts` y `app/(app)/onboarding/page.tsx` queda exactamente como lo dejó FIX-20260822-01. La codificación discutida en F.4 no se ha modificado porque (a) está fuera del alcance y (b) requiere decisión funcional (¿queremos que el redirect venga encodeado o crudo?) que pertenece a ATLAS/INTEGRA, no a SOFIA.
