## 1. Contexto

`QA-20260819-05` (GEMINI, **PASS_WITH_WARNINGS**) cerró los 4 hallazgos de QA-04 (P1-1, P1-2, P2-1, P2-2) con evidencia independiente, pero registró un hallazgo **nuevo, ambiental, preexistente**:

> **P2-RLS:** `audit_log` no tiene política RLS de `INSERT` para el rol docente. RLS es default-deny → los inserts de auditoría (8 call-sites `auditPostIA` en routes IA + `updateBloque`/`updatePlaneacion`) son rechazados en runtime real.

**Evidencia determinista (análisis estático, QA-05 §C):**
- `0014_rls_policies.sql:36` → `alter table audit_log enable row level security;`
- `0014:143-146` → sólo `audit_log_docente_own` y `audit_log_director_cct`, **ambas `for select`**.
- Ninguna política `for insert`/`for update`/`for delete` existe sobre `audit_log`.
- Los 8 write-sites usan `createClient()` (`lib/supabase/server.ts`), cliente scoped a la sesión docente (anon key + cookies → `auth.uid()`), **no** service-role.
- `0020_ia_trazabilidad.sql` (artefacto pendiente de aplicación) agrega `ia_sugerencia` con política `for insert with check (docente_id = auth.uid())` pero **no** agrega INSERT a `audit_log`, pese a que su header (`:13-16`) declara que la trazabilidad interim opera vía `audit_log`.

**Impacto (QA-05 §D):** en Supabase real, cada POST F1/F2/F3 + cada PATCH updateBloque/updatePlaneacion → response 200/422 al cliente + `console.error '[audit_log] insert failed'` (código RLS) + **0 filas persistidas** en `audit_log`. El audit trail P-PD9 no se materializa. No rompe el flujo de la docente (fail-loud por diseño, Decisión 9 ADR-02) ni los AC del incremento (validados contra mock), pero compromete la trazabilidad persistente que P1-1 buscaba restaurar.

**Condición de cierre (QA-05 §D):** verificación en entorno real de que el insert persiste, **o** política INSERT migrada y aplicada; evidencia: fila observable en `audit_log` tras un POST IA.

Frank autorizó publicar (prueba real con Tía Lola) tras validación, **sin commit/push/deploy este turno**. P2-RLS es bloqueante para que la trazabilidad sea operativa en producción.

## 2. Opciones consideradas

### Opción A — Migración con política RLS INSERT restringida (cliente sesión-docente)

Agregar a `audit_log` una política `for insert with check (docente_id = auth.uid() and cct = user_cct())`. Los routes siguen usando `createClient()` (sesión-docente); RLS valida la fila a insertar.

**Política (contrato, no archivo de producción — SOFIA genera `0021_audit_log_insert_rls.sql`):**

```sql
-- 0021_audit_log_insert_rls.sql (artefacto pendiente de aplicación)
create policy "audit_log_docente_insert" on audit_log
  for insert to authenticated
  with check (docente_id = auth.uid() and cct = user_cct());
```

- **`for insert`** — sólo abre INSERT. UPDATE/DELETE siguen default-deny (no se abren). La tabla `audit_log` es un log inmutable (comment 0013:70); no debe haber UPDATE/DELETE en hot path.
- **`to authenticated`** — sólo usuarios autenticados. `auth.uid()` es NULL para anónimos → `docente_id = NULL` → false; doble defensa.
- **`with check (docente_id = auth.uid() and cct = user_cct())`** — valida que la fila a insertar tenga el UUID del usuario autenticado **Y** el CCT del usuario autenticado.
  - El docente **no** puede insertar filas para otro `docente_id` (no falsifica acciones de otros).
  - El docente **no** puede insertar filas para otro `cct` (no falsifica acciones en otro CCT).
  - El docente **sí** puede insertar filas para sí mismo con cualquier `endpoint`, `method` (dentro del `check (method in ('GET','POST','PATCH','DELETE'))` del schema 0013:61), `body_hash`, `response_status` — metadatos de **sus propias acciones**, no datos sensibles.

### Opción B — Acción server-side privilegiada (service-role key)

Crear un cliente service-role en los routes IA (y en `update-actions.ts`) y usarlo para el insert de `audit_log`. El server controla el payload; RLS bypaseado para el insert.

**Requisito:** `SUPABASE_SERVICE_ROLE_KEY` en `process.env` del route handler (Next.js serverless en Vercel).

### Opción C — RPC/trigger transaccional (cierre total)

Migración `CREATE FUNCTION` `SECURITY DEFINER` que inserta `audit_log` transaccional con la respuesta del route. Requiere migración + `supabase db push`. Es el cierre total de Decisión 3 ADR-02 (junto con `ia_sugerencia` en 0020).

## 3. Decisión

**Opción A — Migración con política RLS INSERT restringida**, como migración nueva `0021_audit_log_insert_rls.sql` (separada de `0020`), artefacto pendiente de aplicación hasta que Frank autorice `supabase db push`.

### Justificación

**1. Mínima y consistente con el modelo de seguridad existente.**
- El patrón `with check (docente_id = auth.uid() and cct = user_cct())` es **idéntico** al de `entrega` (`0014:129-131`, `for all`) y `bitacora` (`0014:136-138`, `for all`). `ia_sugerencia` en `0020:48-50` usa `for insert with check (docente_id = auth.uid())`.
- No introduce un nuevo modelo de autorización; extiende el patrón RLS por CCT ya vigente.

**2. No abre escritura arbitraria.**
- `for insert` (no `for all`) deja UPDATE/DELETE en default-deny. La inmutabilidad del log (comment 0013:70) se preserva a nivel de política.
- El `with check` acota la fila insertable al propio docente + propio CCT. No hay ruta para escribir en `audit_log` de otro docente ni otro CCT.
- El schema ya valida lo crítico: `cct text not null references cct(clave)` (FK, 0013:58), `docente_id uuid references docente(id)` (FK, 0013:59), `method check in ('GET','POST','PATCH','DELETE')` (0013:61). El docente no puede insertar valores arbitrarios fuera de estos dominios.

**3. No expone PII ni abre canal al proveedor.**
- Las columnas insertadas por `auditPostIA` (`audit-post.ts:80-87`) son: `cct`, `docente_id`, `endpoint`, `method`, `body_hash`, `response_status`. Ninguna contiene PII ni prompt crudo.
- `body_hash` es `sha256` truncado (16 hex, `audit-post.ts:112-114`) sobre payload **ya anonimizado** post-`anonymizeRequest` (cadena verificada por GEMINI en QA-05 §B). Unidireccional; la entrada del hash no contiene PII.
- `ip`/`user_agent` son nullable y no se insertan este turno (`audit-post.ts` no los envía).
- D-FIN-13 (server-side + anonimizador + cero datos de menores) preservado: la política RLS no toca el flujo al proveedor.

**4. No introduce un secreto de alto privilegio.**
- A diferencia de la Opción B, no requiere `SUPABASE_SERVICE_ROLE_KEY` en el runtime serverless. La service-role key bypasa RLS completamente; cualquier fuga compromete **toda** la base de datos (lectura/escritura de cualquier tabla, cualquier tenant). Introducirla para resolver un insert de auditoría que RLS resuelve nativamente con un `with check` es desproporcionado y antipatrón Supabase.
- Si un route tuviera un bug (p.ej. `endpoint` tomado del body del cliente sin validación), la Opción B insertaría datos falsos con privilegios totales; la Opción A limita el daño al propio docente + propio CCT.

**5. Cierre incremental del cierre total (Opción C).**
- La Opción A resuelve el bloqueo ambiental P2-RLS **sin** depender de `0020` (cierre total con `ia_sugerencia` + trigger/RPC transaccional). Permite a Frank aplicar el fix RLS de forma aislada sin comprometerse al cierre arquitectónico mayor.
- Si Frank decide aplicar `0020` + `0021` juntos, no hay conflicto: políticas disjuntas sobre tablas distintas (`ia_sugerencia` vs `audit_log`).
- La Opción C (trigger/RPC transaccional) sigue siendo el cierre futuro aditivo (Decisión 3 ADR-02): cuando se aplique, el trigger reemplaza el insert best-effort del route por una inserción atómica. La política INSERT de la Opción A es compatible con ese cierre (el trigger `SECURITY DEFINER` opera fuera de RLS; la política queda como defensa en profundidad para inserts directos).

### Por qué migración nueva `0021` y no adición a `0020`

- `0020` es **cierre total** (tabla `ia_sugerencia` + políticas + índices; alcance arquitectónico mayor). Mezclar un fix RLS ambiental preexistente diluye su propósito y acopla dos resoluciones con criticidad distinta.
- `0021` es **fix ambiental** (una política, una tabla). Permite a Frank aplicar el fix RLS **sin** aplicar `0020` (que crea una tabla nueva + índices, mayor superficie).
- `0020` ya tiene un header explícito de "ARTEFACTO PENDIENTE DE APLICACIÓN" (`0020:10-11`); `0021` sigue el mismo patrón.
- Numeración contigua; sin conflicto de schema (tablas distintas).

---

## 4. Riesgo residual aceptado: "forja" de filas propias

**Riesgo:** un docente malintencionado podría insertar filas falsas de auditoría para **sí mismo** (p.ej. simular que usó la IA cuando no lo hizo, o inflar `response_status`), porque el `with check` sólo valida `docente_id` + `cct`, no el contenido semántico de `endpoint`/`body_hash`/`response_status`.

**Evaluación:**
- Es un riesgo de **auditoría débil** (integridad del log), **no** de seguridad ni de PII. El docente es el actor legítimo de sus propias acciones; falsificar "usé la IA" no expone datos de otros docentes ni otros CCT.
- No compromete P-PD9 (IA sólo sugiere, la maestra acepta): la forja de `audit_log` no altera `bloque` ni `planeacion`; sólo ruido en el log.
- Aceptable para MVP (prueba real con Tía Lola, 1 docente de confianza que es la propia tía de Frank).

**Mitigación estructural existente (no requiere acción este turno):**
- `bloque.origen ∈ ('ia_sugerencia','maestra_editado_de_ia', ...)` (SPEC §6.1) es la **fuente de verdad** de aceptación. `audit_log` es el trail temporal; `bloque.origen` es el estado persistido. Un docente que forje `audit_log` no altera `bloque.origen`.
- El cierre total (Opción C / `0020`): `ia_sugerencia` con `texto_propuesto`/`texto_aceptado`/`aceptada` + trigger/RPC `SECURITY DEFINER` que inserta transaccional con la respuesta del route. Cuando se aplique, el trigger reemplaza el insert best-effort del cliente; la política INSERT de la Opción A queda como defensa en profundidad para inserts directos residuales.
- Para escala (multi-tenant real): el cierre total es obligatorio; la Opción A es suficiente para la prueba con Tía Lola.

## 6. Consecuencias

- **Positivas:**
  - Audit trail P-PD9 operativo en runtime real (los 8 call-sites persisten filas reales).
  - Consistencia con el patrón RLS por CCT vigente (`entrega`, `bitacora`, `ia_sugerencia`).
  - Sin secreto de alto privilegio en el runtime serverless.
  - Migración aditiva, reversible (`drop policy "audit_log_docente_insert" on audit_log;`).
  - Compatible con el cierre total futuro (Opción C / `0020`): el trigger `SECURITY DEFINER` opera fuera de RLS; la política queda como defensa en profundidad.
- **Negativas:**
  - Riesgo residual de "forja" de filas propias (§4) — aceptado para MVP, cerrado por `ia_sugerencia` + trigger en el cierre total.
  - Requiere migración (autorización de Frank para `supabase db push`).
  - El insert sigue siendo best-effort (no transaccional con la respuesta del route). El cierre transaccional es la Opción C, diferida.
- **Reversibilidad:** alta. `drop policy "audit_log_docente_insert" on audit_log;` revierte sin afectar datos, código, ni otras políticas.

## 7. Verificación (cómo se confirma que P2-RLS está cerrado)

| Comprobación | Medio | Estado esperado |
|---|---|---|
| `audit_log` tiene política `for insert` tras aplicar `0021` | `select polcmd from pg_policies where tablename='audit_log';` | una fila con `polcmd='insert'` |
| Insert de un POST F1 persiste en runtime real | POST a `/api/planeaciones/[id]/ia/variantes-bloque` con sesión docente válida + Supabase real | `select * from audit_log where endpoint='planeaciones_variantes_bloque' order by created_at desc limit 1;` devuelve 1 fila con `method='POST'`, `cct` real, `body_hash` 16 hex |
| Insert de un PATCH updateBloque persiste | Aceptar una sugerencia F1 → `updateBloque` | 1 fila con `method='PATCH'`, `endpoint='update_bloque_post_ia'` |
| Docente no puede insertar para otro `docente_id`/`cct` | Intento directo (p.ej. script con sesión docente A insertando `docente_id=B`) | RLS rechaza (42501 / `new row violates row-level security policy`) |
| `console.error '[audit_log] insert failed'` desaparece en runtime real | Logs Vercel tras un POST IA | 0 ocurrencias (antes: 1 por POST) |

**Nota de entorno:** la verificación runtime requiere Supabase real (local o staging). QA-05 declaró "sin Supabase local/staging disponible" → la verificación es **gate de staging/producción**, no de DONE local del fix DDL. La corrección por análisis estático (política presente + `with check` correcto + patrón consistente) es determinista y verificable por GEMINI sin runtime.
